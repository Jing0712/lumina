# DESIGN.md — LUMINA

## Components

LUMINA consists of the provided React UI, a public Gateway service, a private Agent service, a background document Worker, and MongoDB Atlas. The UI is deployed on Vercel, the Gateway is publicly reachable, and the Agent and Worker run inside Fly.io’s private network. MongoDB contains the `threads`, `messages`, `memories`, `documents`, `chunks`, `jobs`, and `searchCache` collections, as well as files stored in GridFS. Search results use a two-level cache: an in-process LRU cache for fast repeated access and the MongoDB `searchCache` collection for persistence across restarts. Each completed request also produces a `runs/<requestId>.json` log containing its tool calls, cost, token usage, depth, timing, and termination reason.

## Responsibilities

The Gateway is the only backend component that the browser can directly reach. It checks `X-User-Id`, creates or forwards `X-Request-Id`, validates requests, applies general per-user rate limits, logs the request, and passes SSE events between the browser and the Agent. It does not hold provider keys, call the LLM, or decide how research is performed. The Agent is the only component allowed to hold provider keys and call the LLM, search provider, and embedding provider. It runs the bounded agent loop, manages citations, enforces tool and time caps, and applies `DEEP_DAILY_CAP`; this cap belongs in the Agent because a Gateway-only cap could be bypassed by calling the Agent directly. Quick or Deep mode is explicitly selected by the user, and the Agent never upgrades a Quick request to Deep on its own. The Worker only claims and processes document-ingestion jobs and does not answer questions or communicate directly with the browser.

## Communication

The browser communicates with the Gateway through HTTP, while answer progress is returned through SSE in the required order, including trace, sources, tokens, and the final result. The Gateway forwards requests to the Agent through HTTP and preserves the same request ID so one request can be traced across both services. If the Agent fails before streaming begins, the Gateway returns `502`; if the stream has already started, it sends an error event and closes the stream instead of ending silently. If the user closes the page, the Gateway aborts its upstream request so the Agent does not continue using tools and spending money for an abandoned answer. Document uploads return `202` after the file and job record are stored, and the Worker later polls MongoDB to process them. When multiple Workers are running, each job is claimed with an atomic `findOneAndUpdate` operation that changes its status from `pending` to `running`, preventing two Workers from processing the same job.

## State

MongoDB is the authoritative store for conversation history, long-term memory, uploaded documents, ingestion jobs, daily deep-search usage, persistent search-cache entries, and usage statistics. The Agent owns the per-user deep-search counter and updates it atomically in MongoDB using the user ID and date, allowing `DEEP_DAILY_CAP` to remain correct across multiple Agent instances or restarts. Uploaded original files in GridFS are authoritative, while parsed and embedded records in `chunks` are derived data that can be regenerated from the original files if necessary. A document remains `pending` or `running` until parsing, chunking, embedding, and indexing are complete, and it becomes `indexed` only after a read-your-write probe confirms that one of its chunks is searchable. The LRU cache and MongoDB `searchCache` are disposable because missing search results can be fetched again, but deleting them may temporarily increase latency and provider cost. Run logs are the authoritative evidence for evaluation and observability, even though they do not affect the answer itself.

## Trade-offs

We separate the public Gateway from the private Agent to keep provider keys and cost controls away from the browser, but this adds another deployment and network boundary that can fail. We use asynchronous document ingestion so uploads return quickly and large files do not block requests, although users must wait for the document to become `indexed` before querying it. We use MongoDB Atlas Vector Search instead of a separate vector database so files, metadata, jobs, and embeddings stay in one system, but the Atlas M0 tier permits only three search indexes; `memories_vector`, `chunks_vector`, and `chunks_text` already use all three and future retrieval features may require a paid tier. One decision we are still unsure about is running the Worker beside the Agent: it simplifies deployment and shared configuration, but CPU-heavy PDF parsing or embedding work could slow down live answers. A separate Worker deployment would provide better isolation and scaling, but it would increase operational complexity for this assignment.
