# DESIGN.md — LUMINA

## Components

LUMINA has our own Next.js (React) UI in `web-next/`, which replaces the provided `web/` UI and is deployed on Vercel, a public Gateway running on Fly.io in the `sjc` region, and a private Agent service running in the same Fly.io region. The document Worker is logically a separate component, but it currently runs inside the same process as the Agent rather than as a separately deployed service. For Deep searches, the Agent contains a planner and creates parallel subagents, with one isolated subagent assigned to each planned sub-question. MongoDB Atlas M0 in AWS `us-west-2` stores GridFS files and the `threads`, `messages`, `memories`, `spaces`, `documents`, `chunks`, `jobs`, `usage`, `runs`, `requests`, `searchCache`, and `answerCache` collections. Search uses an in-process LRU cache followed by the MongoDB `searchCache`, while semantic answer caching uses an in-memory lookup with MongoDB persistence for startup prewarming. Locally, each request produces `runs/<requestId>.json`; in deployment, run records are also written to MongoDB because Fly’s local filesystem is temporary, and they are exported for evaluation when needed.

## Responsibilities

The Gateway is the only backend component reachable by the browser. It validates `X-User-Id`, creates or forwards `X-Request-Id`, applies general per-user rate limits, writes one structured log line for each request, and forwards HTTP and SSE traffic to the Agent. It does not connect to MongoDB, calculate application statistics, store provider credentials, or call an LLM, search provider, or embedding model. The Agent writes the records in the `requests` collection, and `/stats` is calculated from those Agent-side records.

The Agent owns provider keys, selects tools, enforces the Quick and Deep tool and time caps, and enforces `DEEP_DAILY_CAP` using MongoDB `usage` records. This cap must remain in the Agent so that it cannot be bypassed by calling the Agent directly. The user explicitly selects Quick or Deep, and the Agent never upgrades a Quick request to Deep by itself.

For Deep mode, the main Agent creates the research plan and assigns each sub-question to an isolated subagent. A subagent can research only its assigned question, cannot see the complete user conversation or other research branches, and returns cited research notes rather than a final answer. The main Agent combines the notes, removes duplicate sources, creates one contiguous citation numbering, and writes the final response. A source receives a citation number only when its supporting snippet has been verified against the fetched page; failed or unverified sources may appear in the trace but cannot support the answer.

The Agent also decides whether semantic answer caching is allowed. It is used only for Quick-mode web questions that can be answered independently. Deep searches, document-space questions, time-sensitive questions, and context-dependent follow-ups such as “What is its price?” bypass the answer cache. Users who have saved long-term memories also bypass the answer cache; for them the Agent recalls memories before searching and folds any that change what to look for into the query. The co-located Worker is responsible only for claiming and processing document-ingestion jobs; it does not serve user questions.

## Communication

The browser sends HTTP requests only to the Gateway, and answer progress is returned through SSE so plans, traces, verified sources, tokens, and the final result can appear as they are produced. The Gateway communicates with the Agent over HTTP and preserves the same request ID across both services. The public Gateway intentionally provides HTTP/1.1 rather than HTTP/2 because Node 26’s built-in `fetch` allowed only one active stream at a time on an HTTP/2 connection during the benchmark. Concurrent benchmark requests were therefore queued behind each other, increasing time to first token from roughly 2 seconds to as much as 20 seconds. With HTTP/1.1, the Node client opens multiple connections and the requests can stream in parallel.

If the Agent connection fails before the Agent has responded, the Gateway retries the request once. It does not retry after streaming has begun because repeating an active agent run could duplicate tool calls, citations, and cost. A failure before headers are sent becomes a `502`; a failure after the SSE stream has started is reported through the stream before it is closed. If the browser disconnects, the Gateway aborts the upstream request so the Agent does not continue spending money for an abandoned answer.

Hedging applies only to the streaming LLM call that writes the final answer. If that call has not responded after 1.2 seconds, the Agent sends an identical request and uses whichever response arrives first. Non-streaming calls, including the Deep planning call, are not hedged. A keep-warm task periodically touches the LLM, search, embedding, and database connections without making paid authenticated calls, reducing the chance that the first evaluated request encounters a cold connection.

For document ingestion, the upload route stores the GridFS file and job record, returns `202`, and immediately wakes the Worker; periodic polling remains as a fallback. Workers claim jobs through an atomic `findOneAndUpdate` transition from `pending` to `running`, so only one Worker can claim a given job even if more Workers are added later.

## State

MongoDB is the durable source of truth for conversations, explicit long-term memories, spaces, original GridFS files, document metadata, ingestion jobs, Deep daily usage, deployed run logs, and request statistics. The Agent owns the Deep daily limit, while the `usage` collection keeps its per-user, per-day count durable across restarts and usable by multiple Agent instances. The Agent writes the `runs` and `requests` collections, which support deployed observability, `/stats`, and evaluation. Local JSON run files are development or exported copies rather than the only durable record.

Original GridFS files are authoritative, while `chunks` and embeddings are derived data that can be regenerated from the original files. A document is not marked `indexed` until a read-your-write probe confirms that at least one of its chunks is searchable.

The two cache systems have different consistency behavior. Search first checks the in-process LRU and then checks MongoDB `searchCache` after an in-memory miss. Therefore, search-cache entries written by one Agent instance can be discovered by another instance without restarting. Both layers are disposable because a missing result can be fetched from the search provider again.

Semantic answer-cache queries, however, check only the current Agent process’s memory. MongoDB `answerCache` provides persistence and is loaded into memory when the process starts, but it is not checked again after each memory miss. As a result, an answer written by one Agent instance will not become visible to another running instance until that instance restarts and reloads the cache. The current single-Agent deployment avoids this inconsistency, but horizontally scaling the Agent would require MongoDB lookup or another shared cache on every answer-cache miss.

Answer-cache entries are separated by user and expire after their TTL. They are not read or written for Deep searches, document-space questions, time-sensitive questions, context-dependent follow-ups, or users who have saved long-term memories. The Gateway’s general rate-limit counter is also held in the memory of one Gateway instance, so it cannot coordinate limits across multiple Gateway replicas. The current deployment therefore assumes one Gateway instance for general rate limiting, even though the MongoDB-backed Deep usage counter remains durable across instances.

## Trade-offs

Separating the public Gateway from the private Agent keeps provider keys, Deep limits, and expensive tools outside the browser-facing security boundary. The cost is an additional network hop and another connection that can fail, which is why the Gateway has one limited pre-response retry and end-to-end request IDs.

Parallel isolated subagents give each Deep sub-question its own context and reduce interference between research branches. They also allow several branches to run at the same time, but each branch makes an additional model call to produce its research notes. In the deployed evaluation, mean Deep cost increased from about `$0.096` to `$0.115` per answer after this change, although it remained below the assignment limit.

Semantic answer caching greatly reduces repeated-query latency and cost; mean Quick cost fell to approximately `$0.0022`. The trade-off is the risk of replaying an answer whose information is no longer current or whose wording depends on earlier conversation context. We reduce this risk by limiting caching to independent Quick web questions, isolating entries by user, applying expiration, and bypassing the cache for time-sensitive, document-based, Deep, and context-dependent requests. The current in-memory lookup also favors speed but assumes a single Agent instance.

Hedged final-answer requests reduce the impact of occasional slow streaming model responses by starting a duplicate after 1.2 seconds. This improves tail latency, but occasionally both calls may consume provider resources and incur cost. We therefore apply hedging only to the latency-sensitive final streaming call rather than to every model call.

We were initially unsure whether running the Worker inside the Agent process would slow live answers during PDF parsing and embedding. In the deployed benchmark, search latency during ingestion was between `0.08×` and `0.73×` the idle-search latency, so the tested workload showed no slowdown. Keeping them together therefore simplifies deployment for this assignment. However, this result does not prove that the design will remain safe with much larger files, several simultaneous uploads, or heavier multi-user traffic. If those workloads become common, moving the Worker into a separate process or Fly application would provide stronger resource isolation.
